# preview-circuit-board

plan.md §3.12 が mx-redstone に要求する 2 本目の検証手段
——「**回路盤プレビュー（部品を置いて動かすサンドボックス）**」——である。
plan.md §6 Step 2 の完了条件は「テスト green **かつ** 内蔵プレビューが操作可能」であり、本アプリがその後半にあたる。

**これはパッケージではない。** plan.md §4.1 のとおり `apps/preview-*/` に置かれた dev アプリであり、
`index.ts` から export されず、他リポジトリから import できない。`pnpm verify` はこれを実行しない。

```console
$ pnpm preview                          # 対話モード（wire-run シナリオ）
$ pnpm preview --list                   # シナリオ一覧と、それぞれが何を確かめるものか
$ pnpm preview --stats                  # 数値レポート（下記「見つけたもの」の出所）
$ pnpm preview --once --ascii --levers-on --scenario piston-push --ticks 2
```

## 何が見えるか

3 つのビュー（`v` で巡回）。

| ビュー | 何を示すか |
| --- | --- |
| `board` | 部品と、電力レベルに応じた色。回路の**印象** |
| `power` | 各セルの電力 0–15 を 16 進数 1 桁で。回路の**測定値** |
| `timeline` | 監視セルの電力を**tick 軸**に沿って並べたテープ |

**timeline がこのアプリの存在理由である。** テストは最終状態を assert する。
「2 tick 遅れて届いた信号」は最終状態が同じなので**テストからは見えない**。
tick 軸に並べれば一目で分かる。同じ理由で `tick` カウンタは常時表示している。

置く・消す・倒す・押す・回す・1 tick 進める・N tick 進める・安定するまで進める、が全部キー 1 つである
（`?` でキー一覧）。ピストンは `domain/piston.ts` の `planPush` を呼び、**拒否理由**（`immovable` /
`too-long`）を HUD に文字で出す。理由の出ないピストンは「何もしなかった」と区別がつかない。

## 何が見えないか

- **ピストンが押すのはこの盤面のブロックだけである。** プレイヤーも世界も無い。
  `redstone:effects` は今なお `Effect.void`（`stages/registration.ts:162`）であり、
  ピストンの実際の移動は本アプリ内の `board.ts#applyPistons` が代行している。
  **このプレビューが動いていることは `redstone:effects` が動く証拠にならない。**
  証拠になるのは「`planPush` の判断が正しい」ところまでである。
- **隣接は 2D の 4 近傍である。** 本物は「ボクセルの 6 面」で、それは mc-kernel の座標型の持ち物である
  （`domain/power-graph.ts:23-27`）。上下方向の回路、斜め接続、ブロック越しの強電化 (strong power) は表現できない。
- **未実装の部品は出せない。** ディスペンサ・ホッパー・オブザーバ・感圧板・コンパレータは
  `ComponentKind` に無い（README 現状）。
- **ブロック名簿は 2 つだけの fixture である。** `pistonImmovable` の権威は mc-kernel の能力表であり
  （`domain/piston.ts` 冒頭）、`BlockCapabilityLookup` が引数なのは、こういう呼び出し側が
  2 個で済ませられるようにするためである。

## 見つけたもの

`pnpm preview --stats` は全部**実行時に測定**しており、記録された期待値は 1 つも無い。
直せば finding は自動的に消える。初回実行（2026-07-26）は 7 件だった。

### 直したもの（4 件 + 1 件）

| # | 症状 | 原因と決着 |
| --- | --- | --- |
| F2 | **リピーターが自分をラッチして二度と落ちない** | `propagateTick` がソースの電力を**全隣接**に流すため、リピーターは自分の入力セルを 12 → 14 に持ち上げ、次 tick に自分自身から再点火していた。`Component.outputTo` と `conductsInto` で、駆動先を正面 1 セルに限定（DN-RS-12） |
| F3 | **リピーターが側面にも給電する** | 同じ原因・同じ修正。プレイヤーが回路を**分離**するために置く部品で、DN-RS-5 が警告する「2 回路の無言の溶接」が起きていた |
| — | **トーチが 2 tick 周期で点滅する**（`--stats` ではなく `torch-inverter` シナリオ自身の主張が偽だった） | 同じ原因。トーチが自分の反転対象ワイヤを駆動していた。バニラでも参照実装でもトーチは支持セルに給電しない（testing.md §7）。`conductsInto` が `invertedBy` を除外 |
| F5 | **`settle` が非循環回路を OSCILLATING と報告する** | `SETTLE_TICK_LIMIT = MAX_POWER_LEVEL + 2 = 17` の根拠が「ワイヤ最長走行距離 + 2」だが、収束時間を決めるのは減衰ではなく**直列の遅延素子数**。定数を廃し `settleTickLimitFor(board)`（遅延素子数 + 2）へ（DN-RS-4） |
| F6 | **ランプが隣のランプを光らせる** | `propagateTick` は正しい（ランプは伝導しない）。漏れていたのは `isLit` で、隣接セルの電力を見ていた。**自分に給電しているセル**に限定し、sweep と同じ `conductsInto` を共有（DN-RS-5 §5-1） |

### 残したもの（3 件）——ただし**テストで名指し済み**

| # | 症状 | 残す理由 |
| --- | --- | --- |
| F1 | 信号がワイヤ 14 マスしか進まない（vanilla は 15） | **算術の主張は直した**（15 と書いてあった全箇所を 14 に）。挙動は残す——閉じるには「ソースは最初の隣接セルへ減衰しない」が要り、全回路の全レベルが変わる |
| F4 | リピーターの遅延が常に 1 tick | `Component.delayTicks` は**削除した**。実装には「N tick 前の入力」という記憶が要り、`propagateTick` の (board, previous) という設計を変える話である |
| F7 | 押したボタンが戻らない | パルスは**残り時間**＝状態。解放は `stages/registration.ts`（dt を tick に換算し盤面 `Ref` を持つ）の仕事である |

**F2・F3・F6 は当時の 21 本の電力グラフテストが 1 つも捕まえていなかった。**
理由は F2 の detail に書いたとおりで、テストは最終状態を assert し、
これらの最終状態は**期待どおり**だった——壊れていたのは「電源を外したあと」と「隣に何があるか」である。

**`--stats` の行は pin ではない。** 実行時に測って期待値を記録しないので、
直すと finding は「固定される」のではなく「静かに消える」。
だから確認できた finding は `test/power-graph.test.ts` に assertion として落とす。
上の 8 件はすべてそこにある——**直したものは修正を固定するテストが、
残したものは現在の挙動を名指しするテストが**。レポートは読まれなければ効かないが、テストは落ちる。

**チェック自体は残してある。** 直った 4 件の測定は今も毎回走っており、
ただ finding を出さないだけである。合格したら消すチェックは、コードを 1 回しか検査しない。

## 制約

- `apps` は `SCAN_ROOTS` に入っている（`scripts/check-dependency-whitelist.ts`）。
  したがって import は他のソースと同様にゲートされる。**依存は 0 個**——色ライブラリすら足していない。
- `Date.now()` / `new Date()` / `performance.now()` 禁止も適用される。
  **エスケープハッチ (`mc-kernel-allow-time-source`) は使っていない。** 時計を読む場所が 1 つも無いためである。
  tick はキー入力で進む。固定レートの意味を考えれば、これは制約ではなく正しさである
  （`stages/registration.ts:11-27`）。
- 型検査は `tsconfig.preview.json`（`types: ["node"]`）。
  `tsconfig.build.json` は**触っていない**——出荷ソースが Node 型を持たないという証明はそのまま残る。
